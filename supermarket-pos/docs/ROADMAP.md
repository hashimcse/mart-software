# Roadmap

This mirrors the 13-phase plan from the spec. Each phase should leave the app in a working, runnable state before the next one starts.

- [x] **Phase 1 — Architecture, database, authentication.** Monorepo scaffold, complete Prisma schema (every core entity), JWT auth with rotating refresh tokens, RBAC (5 roles / ~20 permissions), audit logging on auth events, login UI + protected shell.
- [x] **Phase 2 — Product/category/brand management.** Server-side search/pagination for products, category hierarchy (with delete-guard against attached products/subcategories), brand CRUD, custom units, barcode/SKU uniqueness enforced at the DB level with friendly conflict errors, price changes gated behind a separate `products.price.edit` permission, local image upload served statically. Demo catalog data seeded (8 products across 4 categories, 3 brands).
- [x] **Phase 3 — POS + barcode scanning.** Keyboard-first POS screen (F1 search, F2 clear, F4 hold, F5 amount received, F8 complete, Delete removes selected line), a single input that handles both scanner input and manual product search, live cart with per-line discounts, hold/resume bills, a lightweight customer picker with quick-add, and real sale completion: atomic invoice numbering, race-safe stock deduction (two terminals selling the last unit of something resolves correctly rather than going negative), decimal-safe tax math (inclusive and exclusive), and discount amounts gated by `discounts.apply` / `discounts.apply_large`. Cash payments show change due; other methods record the payment as-is. Split payments across multiple methods and thermal receipt printing are Phase 4.
- [x] **Phase 4 — Billing + thermal printing.** Split payments (any mix of methods, cash covers the remainder and can produce change, verified against 11 scenarios including a 3-way split with a non-round total). Real ESC/POS byte generation (init/align/bold/cut — verified byte-for-byte, not just "looks right") dispatched over a raw TCP socket to a network printer's port 9100 (verified against an actual local TCP listener, plus verified graceful failure on an unreachable printer). Browser-native printing via a dedicated print window sized exactly for 58mm/80mm paper, for printers installed as a normal system printer. Print/reprint from the recent-sales list and the post-sale confirmation. A lightweight Settings page for store info and printer configuration (paper width, browser vs. network mode, printer IP/port, test print) — built on the `settings` table the schema already had.
- [x] **Phase 5 — Inventory.** Stock adjustments, damaged/expired write-offs, and sales all go through the same race-safe guarded-update pattern (checked with 5 boundary-case unit tests: below/at/above threshold, zero-stock exclusion, fractional weighted quantities). Low-stock, out-of-stock, and expiring-soon alert lists; a stock valuation report (cost basis, retail value, potential profit — verified against hand-computed numbers); a filterable, paginated movement ledger; a shelf/aisle location field on products. The Dashboard's placeholder metrics are now real numbers (today's sales, transactions, low-stock count) instead of "—".
- [x] **Phase 6 — Purchases + suppliers.** Full PO → receive → invoice → pay workflow. Stock only increases when a PO is actually marked received (not on creation) — the first real writer of `MovementType.PURCHASE`, sitting unused in the schema since Phase 1. Supplier outstanding balance is computed from opening balance + non-cancelled purchases − payments (never stored, so it can't drift out of sync) — verified against 3 scenarios including a cancelled purchase correctly excluded and an overpayment correctly producing a credit balance. A purchase auto-transitions to PAID once payments cover its total — verified against 5 boundary cases (exact payment, overpayment, a payment one cent short, and that paying an unreceived or cancelled order never auto-marks PAID). Cancelling is only allowed before stock is received, on purpose — reversing already-received inventory is a purchase return, deferred rather than half-built here.
- [x] **Phase 7 — Customers + loyalty.** Full customer records (walk-in/registered/credit) with search, purchase history, and payment history. Credit balance is computed the same "never store what can drift" way as supplier balances — sum of `CREDIT`-method sale payments minus what they've paid back — verified against 4 scenarios including overpayment correctly producing a credit-in-their-favor balance. Loyalty points accrue automatically on checkout (configurable rate via Settings, truncated down to a whole point — verified against 5 cases including that 999.99 spent doesn't round up to the next point) and can be manually adjusted (earning *and* redemption both go through this — see docs/ARCHITECTURE.md for why that's a deliberate scope call, not a shortcut). The Dashboard's last placeholder card, "Pending payments," is now a real number — all four dashboard metrics are real as of this phase.
- [ ] **Phase 8 — Returns/refunds.** Partial/full returns against an invoice, inventory restoration, refund handling. This is also where purchase returns (deferred in Phase 6) would naturally fit alongside sale returns, since both need the same "reverse a completed transaction safely" machinery.
- [ ] **Phase 9 — Expenses + cash register.** Shift open/close, expected vs actual cash, expense recording. Needs its own concept of "cash physically received" (tendered, including change given) layered on top of Phase 4's `Payment.amount`, which deliberately records only the amount applied to the sale — see docs/ARCHITECTURE.md.
- [ ] **Phase 10 — Reports + dashboard.** Sales/inventory/financial reports, charts, CSV/Excel/PDF export.
- [ ] **Phase 11 — Backup/restore.** Manual + scheduled DB backups, restore flow.
- [ ] **Phase 12 — Security + performance hardening.** Rate limiting sweep, query/index review, load testing the barcode lookup path.
- [ ] **Phase 13 — Testing + deployment.** Automated test suite, deployment docs for multi-terminal LAN setups.

The database schema already models every table these phases need, so later phases are mostly services/routes/UI rather than schema churn.
